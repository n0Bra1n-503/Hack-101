### Interpretation of `NaN`
In this real AWS telemetry stream:
1. `NaN` in sensor channels (`temperature`, `humidity`, `pressure`, `wind_speed`, `rainfall`) represents an unequipped sensor channel, transmission dropout, or sensor offline event.
2. Specifically in `rainfall`, `NaN` indicates either that the station does not have an active tipping bucket rain gauge, or dry non-reporting intervals.
3. In `altitude`, `NaN` represents missing station metadata in the upstream telemetry feed.
4. In relational databases (Supabase PostgreSQL), `NaN` MUST map strictly to `NULL`.

## 11. Duplicate Records

- **Maharashtra**: **0 duplicate `(station_id, timestamp)` pairs** across all 3,179,805 records. Uniqueness is 100% clean.
- **Gujarat**: Exactly **10,006 duplicate `(station_id, timestamp)` pairs**.
  - **Forensic Diagnosis**: 100% of these duplicates (all 10,006 occurrences) belong to a single identifier: `"Bhadar dam"`.
  - **Root Cause**: Two completely distinct physical AWS installations were both named `"Bhadar dam"`:
    - Installation A: Latitude $21.8100^\circ\text{N}$, Longitude $70.7689^\circ\text{E}$ (reports `relative_humidity`, `pressure`, and `rainfall`).
    - Installation B: Latitude $23.3250^\circ\text{N}$, Longitude $73.6917^\circ\text{E}$ (reports `temperature` and `wind_speed`).
  - **Resolution**: Ingestion MUST disambiguate station IDs by appending coordinate or district tokens (e.g. `Bhadar_Dam_Rajkot` vs `Bhadar_Dam_Aravalli`), or coalesce multi-sensor channels using location.

## 13. Data Quality

The real data exhibits genuine, messy, real-world AWS characteristics:

1. **Extreme Physical Outliers / Sensor Glitches**:
   - `temperature`: Values range down to $-141.7^\circ\text{C}$ and up to $+98.9^\circ\text{C}$ (hardware error codes / voltage dropouts).
   - `relative_humidity`: Values reach $+1,016.0\%$ and $-100.0\%$ (sensor calibration fault).
   - `rainfall`: Values reach $9.15\times 10^9\text{ mm}$ and $-509.0\text{ mm}$ (counter rollover / corrupt telemetry).
2. **Channel Asymmetry**:
   - In Maharashtra, 554 out of 555 stations report only pressure, wind, and rain; only 1 station (`CWPRS campus`) reports full temperature.
   - In Gujarat, 526 stations report active temperature, pressure, humidity, and wind speed.
3. **Implication for ML & Quality Flagging**:
   - The data perfectly proves the need for SkyGuard's Multi-Tier Anomaly Detection and Quality Flagging engines!
   - Ingestion should preserve the raw measurement as reported, but set `quality_flag = 'sensor_fault'` or `'unphysical'` when physical bounds are violated.

## 17. Recommended Supabase Strategy

1. **Role of Supabase**:
   Supabase PostgreSQL is the **operational online data plane**, NOT an archival file dump.
   - It serves indexed API queries for FastAPI (`GET /api/v1/readings`, `GET /api/v1/stations`).

2. **Archival vs Operational**:
   - The multi-gigabyte raw JSONL files remain in read-only raw storage (external object storage / cloud bucket).
   - Only validated, normalized records are ingested into Supabase PostgreSQL.
3. **Storage Tiering**:
   Because full ingestion of 5.36 million records requires ~1.5 GB in PostgreSQL table storage, the team should:

   - Retain the full 5.36M record dataset in processed Parquet files for analytical/ML training tasks.

## 20. Transformation Required

A streaming transformation pipeline must perform the following transformations:

1. **Line-by-Line Streaming**: Read JSONL line-by-line using Python generator to keep memory footprint $< 100\text{ MB}$.
2. **Station Disambiguation**:
   - Check if `station_id == 'Bhadar dam'`.
   - If latitude $\approx 21.81$, assign `station_id = 'Bhadar_Dam_Rajkot'`.
   - If latitude $\approx 23.32$, assign `station_id = 'Bhadar_Dam_Aravalli'`.
3. **Deterministic `reading_id` Generation**:
   $$\text{reading\_id} = \text{SHA256}(\text{station\_id} + \text{"\_"} + \text{timestamp})[:24]$$
4. **Variable Normalization**:
   - `relative_humidity` $\to$ `humidity`
   - `atmospheric_pressure` $\to$ `pressure`
   - `altitude` $\to$ `elevation`
   - Float `NaN` $\to$ Python `None` (SQL `NULL`)
5. **Physical Range Auditing & Quality Flagging**:
   - If $T < -50^\circ\text{C}$ or $T > 60^\circ\text{C} \implies \text{quality\_flag} = \text{'extreme\_temp\_fault'}$
   - If $H < 0\%$ or $H > 100\% \implies \text{quality\_flag} = \text{'humidity\_sensor\_fault'}$
   - If $R < 0\text{ mm}$ or $R > 500\text{ mm/hr} \implies \text{quality\_flag} = \text{'rainfall\_telemetry\_fault'}$
   - Else $\text{quality\_flag} = \text{'valid'}$.

## 21. Batch Ingestion Strategy

1. **Chunking**: Ingest records in batches of **1,000 to 2,000 records**.
2. **Station Seeding First**: Extract unique stations first, insert into `stations` table with `ON CONFLICT (station_id) DO NOTHING`.
3. **Idempotent Upsert**:
   Use PostgreSQL `INSERT INTO readings (...) VALUES (...) ON CONFLICT (station_id, timestamp) DO NOTHING;`
   - Safe to re-run multiple times without duplicate record creation.
4. **Metrics Tracking**:
   Track and log:
   - Total records read
   - Total records inserted
   - Total records skipped (duplicates)
   - Total records flagged (quality issues)
   - Total ingestion duration & records/sec throughput

## 24. Risks / Issues

1. **Schema Mismatch with Backend & Database**:
   The current backend `Reading` model and Pydantic schema enforce `nullable=False` on `wind_direction`, `solar_radiation`, `area`, and `elevation`. Attempting to ingest real data into the current schema will crash immediately.
2. **Station Name Collision (`Bhadar dam`)**:
   Two physical dams share the exact name in Gujarat. Disambiguation logic must be codified before creating a unique constraint on `(station_id, timestamp)`.
3. **Extreme Telemetry Corruption**:
   Rainfall has values over 9 billion mm; humidity has values over 1,000%; temperature drops to -141°C. The backend must not reject the entire record if one sensor channel is corrupt; it must isolate the channel, set quality flags, and allow the Trust Score engine to downweight that sensor.
4. **Channel Sparsity in Maharashtra**:
   Maharashtra stations are largely automatic rain/wind gauges, with 97% lacking temperature. Algorithms relying on multivariate correlation ($T \leftrightarrow H$) must account for single-channel reporting stations.

## 26. Backend Schema Reconciliation

Following the empirical data audit, the backend data models and validation contracts were reconciled to achieve complete compatibility with real IMD AWS observations:

### A. Nullable Fields & Extensibility
The canonical SkyGuard contract is strictly preserved, but fields absent or intermittently reported in the real telemetry are declared as `Optional[float] = None` in Pydantic and `Column(Float, nullable=True)` in SQLAlchemy:
- **Measurement Channels**: `temperature`, `humidity`, `pressure`, `rainfall`, `wind_speed`
- **Extended Canonical Channels**: `wind_direction`, `solar_radiation` (preserved as `NULL` for future station sensor retrofits)
- **Geographic Metadata**: `area`, `elevation` (preserved as `NULL` unless joined with DEM/station registry)

### B. Missing-Value Handling
- Missing telemetry values must **never** be replaced with synthetic zeros or imputed constants (e.g. missing rainfall must never be converted to `0.0 mm`, nor missing temperature to `0.0°C`).
- Missing measurements are explicitly stored and returned as `NULL` (`None`).

### C. Bhadar Dam Disambiguation
Forensic analysis revealed that 100% of duplicate timestamps in Gujarat belonged to `"Bhadar dam"`, where two distinct geographic reservoirs share the identical name:
1. **Bhadar Dam (Rajkot District)**: Lat $21.8100^\circ\text{N}$, Lon $70.7689^\circ\text{E}$ (13,981 records)
2. **Bhadar Dam (Aravalli District)**: Lat $23.3250^\circ\text{N}$, Lon $73.6917^\circ\text{E}$ (12,560 records)

The ingestion service performs deterministic disambiguation:
- Latitudes near $21.81^\circ\text{N} \implies \text{station\_id} = \text{'Bhadar\_Dam\_Rajkot'}$
- Latitudes near $23.325^\circ\text{N} \implies \text{station\_id} = \text{'Bhadar\_Dam\_Aravalli'}$
- Both physical stations remain preserved without deletion or merging, and querying `/api/stations/Bhadar dam/readings` seamlessly returns both physical streams.

### D. Reading ID Strategy
Because raw IMD telemetry lacks a surrogate identifier, a deterministic, collision-safe 24-character hexadecimal identifier is generated:
$$\text{reading\_id} = \text{SHA256}(\text{physical\_station\_id} + \text{"\_"} + \text{timestamp})[:24]$$
By incorporating the disambiguated physical station identifier, collision risk across identical station names or timestamps is eliminated.

### E. Ingestion Validation vs ML Classification
- **Ingestion Responsibility**: Structural integrity, parseability, and coordinate boundaries (e.g. reject non-numeric strings, ensure valid ISO timestamps).
- **No Premature Classification**: Ingestion does **not** evaluate whether $55^\circ\text{C}$ or $0\text{ hPa}$ is genuine weather vs a sensor fault. Classifying anomalies as genuine severe weather, hardware failure, or drift is the exclusive domain of the Multi-Tier ML and Decision Intelligence engines. Extreme weather observations are accepted and persisted verbatim.

### F. Quality Flag Scheme
A lean, structural quality flag scheme is established:
- `'valid'`: Structurally sound observation with standard channels populated.
- `'missing'`: Structurally sound observation with one or more primary sensor channels missing (`NULL`).
- `'malformed'`: Unparseable or corrupt observation rejected before database insertion.
- `'duplicate'`: Duplicate physical observation rejected with HTTP 409 Conflict.
